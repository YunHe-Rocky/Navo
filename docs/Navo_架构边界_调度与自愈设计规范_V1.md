# Navo 架构边界、调度与自愈设计规范（V1）

> 本文档用于固定当前已经确认的产品定位、架构边界、节点切换、调度关系、自愈规则与故障处理原则。  
> 本版重点是“先把边界定清楚”，暂不进入具体代码实现与 UI 视觉稿。

---

## 1. 项目定义

Navo 是一个 **自身代理管控工具，同时具备全局代理状态观测能力**。

核心原则：

> **全局可以看，只有自己可以管。**

Navo 现有功能全部保留。

### 1.1 Navo 可以观察

Navo 可以观察当前 Windows 中的代理相关状态，包括但不限于：

- 当前是否存在代理
- System Proxy 状态
- TUN 状态
- 当前代理模式
- 当前代理来源
- 当前节点
- 直连出口 IP
- 代理出口 IP
- 延迟
- 网络波动
- 丢包
- 上下行流量
- 当前代理链路是否真实可用
- 其他代理软件启动的 sing-box / Mihomo / Xray 等运行状态

### 1.2 Navo 可以控制

Navo **只能控制 Navo 自身创建、启动、配置或接管的资源**。

例如：

- Navo 自己启动的代理核心
- Navo 自己的 System Proxy
- Navo 自己的 TUN
- Navo 自己产生的 Route / DNS / NRPT / Firewall 等网络资源
- Navo 自己的节点配置
- Navo 自己的流量策略

### 1.3 Navo 不控制

对于 Clash、v2rayN 或其他代理软件：

- 可以检测
- 可以识别
- 可以展示

但不能：

- 修改
- 关闭
- 切换
- 删除
- 自愈
- 接管其资源

---

## 2. 代理来源与节点域

Navo 默认状态为空。

Navo 不内置机场、不内置节点、不内置代理线路，全部由用户自行添加。

代理来源分为两类：

### 2.1 机场订阅

用户添加机场订阅后：

1. Navo 拉取并解析订阅；
2. 机场提供多少节点，Navo 就展示多少节点；
3. 用户可以拥有多个机场；
4. 所有机场节点进入机场节点资源池。

示例：

```text
机场 A
├─ 香港 01
├─ 日本 01
└─ 美国 01

机场 B
├─ 新加坡 01
└─ 美国 02
```

### 2.2 独立代理

用户单独购买或添加一条代理线路时，该线路作为一个独立节点保存。

示例：

```text
独立代理
├─ Proxy A
├─ Proxy B
└─ Proxy C
```

### 2.3 唯一活动节点

无论用户保存多少机场、多少机场节点、多少独立代理：

> **任意时刻只能有一个当前活动节点作为 Navo 的主代理出口。**

状态概念：

```text
Active Node = 当前正式活动节点
Candidate Node = 正在尝试切换、尚未正式提交的候选节点
```

候选节点只有在实际网络验证通过后，才能成为 Active Node。

---

## 3. 代理核心域

Navo 当前代理核心固定为：

- sing-box
- Mihomo
- Xray

代理核心域的定位：

> **核心只是执行器和状态提供者，不负责业务决策。**

### 3.1 负责

- 接受上层调度
- 启动 Navo 自己的核心
- 停止 Navo 自己的核心
- 加载节点运行配置
- 返回核心运行状态
- 检测同类核心是否被其他软件启动
- 对外部软件启动的同类核心只展示状态

### 3.2 不负责

代理核心域不能自行决定：

- 什么时候启用代理
- 选择哪个节点
- 使用 System Proxy 还是 TUN
- 使用全局、黑名单还是白名单
- 修改 Route / DNS
- 自行执行跨域自愈
- 控制其他软件启动的核心

---

## 4. 代理接管域

System Proxy 和 TUN 是两种不同的接管实现，但必须由 Navo 统一管理。

### 4.1 接管方式

Navo 的接管状态只有三种：

```text
OFF
SYSTEM_PROXY
TUN
```

硬性规则：

> **System Proxy 与 TUN 任意时刻只能启用一个。**

禁止同时出现：

```text
SYSTEM_PROXY = ON
TUN = ON
```

### 4.2 模式切换

System Proxy → TUN：

1. 完整退出 System Proxy；
2. 确认 System Proxy 已释放；
3. 再启用 TUN。

TUN → System Proxy：

1. 停止 TUN；
2. 完整恢复 Navo TUN 所产生的网络状态；
3. 确认释放完成；
4. 再启用 System Proxy。

互斥关系必须由后端状态机保证，不能只依赖 UI 禁用按钮。

---

## 5. 流量策略域

流量策略与接管方式是两个不同维度。

接管方式解决：

> **流量如何进入 Navo。**

流量策略解决：

> **进入后按照什么规则处理。**

当前策略：

```text
GLOBAL
BLACKLIST
WHITELIST
```

### 5.1 全局

选择全局时：

> 直接由当前接管方式完整托管，不使用用户的黑白名单规则。

可以形成：

```text
System Proxy + Global
TUN + Global
```

### 5.2 黑名单 / 白名单

黑名单和白名单属于 **Navo 的通用流量策略**，不单独属于 System Proxy，也不单独属于 TUN。

因此：

```text
System Proxy + Blacklist
System Proxy + Whitelist

TUN + Blacklist
TUN + Whitelist
```

必须使用同一套用户规则定义。

核心原则：

> **规则统一，执行适配。**

即：

```text
用户规则
   ↓
统一规则模型
   ↓
根据当前接管方式编译/应用
   ↓
System Proxy 或 TUN
```

黑名单/白名单“名单内具体代表代理还是直连”的精确定义，放到后续规则细化阶段确定，不影响本版架构边界。

---

## 6. 网络控制域

网络控制域属于底层执行层。

它不负责决定使用哪个节点，也不负责决定使用 System Proxy 还是 TUN。

它只负责执行 Navo 当前接管事务所需要的 Windows 网络变化。

主要资源包括：

- Navo TUN 虚拟网卡
- Route
- DNS
- NRPT
- Firewall
- 其他明确属于 Navo 的网络状态

原则：

> **只操作能够确认属于 Navo 的网络资源。**

外部资源可以观察，但不得修改。

例如：

- VMware
- Hyper-V
- WSL
- 其他 VPN/TUN
- 其他软件 Route
- 用户自己设置的 DNS

都不能因为与 Navo 预期不一致而被 Navo 擅自修改。

---

## 7. 跨域协调：连接协调器

Navo 必须存在唯一的跨域总协调者。

本文统一称为：

> **Connection Coordinator / 连接协调器**

连接协调器本身不直接：

- 启动核心
- 改 Route
- 改 DNS
- 创建 TUN
- 写 System Proxy

它只负责：

> **一次完整连接事务中，各领域按照什么顺序执行。**

### 7.1 用户切换节点

例如：

```text
节点 A → 节点 B
```

流程：

```text
用户
 ↓
UI
 ↓
连接协调器
 ↓
节点域：读取 B
 ↓
核心域：应用 B 的配置
 ↓
接管域：保持当前接管方式
 ↓
必要时网络控制域完成底层网络动作
 ↓
真实联网验证
 ↓
成功后提交 B 为 Active Node
```

### 7.2 切节点不得改变其他用户选择

例如原状态：

```text
节点 A
TUN
BLACKLIST
```

用户只切换节点后，目标状态必须是：

```text
节点 B
TUN
BLACKLIST
```

节点切换不得擅自修改：

- System Proxy / TUN
- Global / Blacklist / Whitelist
- 用户其他运行偏好

---

## 8. 调度器边界

Scheduler 与 Connection Coordinator 不能混为一谈。

### 8.1 Scheduler 负责

- 定时检测
- 状态刷新
- 页面数据刷新
- 流量采集
- 健康检查触发
- 资源加载
- 资源释放
- 后台静默任务

### 8.2 Scheduler 不负责

Scheduler 不能直接：

- Restart Core
- Enable TUN
- Disable TUN
- Set Route
- Set DNS
- 切换节点

需要发生业务状态改变时，Scheduler 只能产生请求或事件，由连接协调器或对应领域处理。

---

## 9. 连接事务必须串行

Navo 同一时间只允许一个网络状态修改事务。

例如：

```text
IDLE
 ↓
SWITCHING_NODE
 ↓
VERIFYING
 ↓
COMMIT
 ↓
IDLE
```

当正在切换节点时：

- UI 可以继续显示状态
- 观测可以继续运行
- 流量采集可以继续

但其他修改动作必须排队。

例如：

- 自愈
- 自动切换
- 模式切换
- 第二次节点切换

都不能与当前事务并发修改网络。

原则：

> **观测可以并行，控制必须串行。**

---

## 10. 节点切换成功标准

节点切换成功不能以以下条件单独判定：

- Core 启动成功
- 配置加载成功
- 端口监听成功
- TUN 网卡存在

真正成功标准只有一个：

> **目标节点已经真实可用，并且代理链路可以正常访问公网。**

验证至少应覆盖：

- 核心是否正常
- 代理入口是否正常
- DNS 是否正常
- TCP/HTTPS 是否能够正常访问公网
- 代理出口 IP 是否能够获取
- 实际流量是否真正经过当前代理链路

例如：

```text
Core 运行       √
端口监听        √
HTTPS 出网      ×
```

仍然属于：

> **切换失败**

---

## 11. 节点切换事务

当前节点 A，用户主动切换 B：

```text
Active Node = A
Candidate Node = B
```

B 只有完成真实联网验证后，才能：

```text
Active Node = B
Candidate Node = NULL
```

验证失败不能立即提交 B。

---

## 12. 自愈总原则

验证失败是自愈触发点之一。

但：

> **修复动作执行成功，不代表自愈成功。**

只有最终真实网络恢复可用，才算自愈成功。

标准流程：

```text
检测到异常
 ↓
故障归因
 ↓
第 1 次自愈
 ↓
重新验证
 ├─ 成功 → 结束
 └─ 失败
      ↓
第 2 次自愈
      ↓
重新验证
      ├─ 成功 → 结束
      └─ 失败 → 自愈终止
```

硬性规则：

> **一次故障最多执行两轮自愈。**

“两次”指两轮完整自愈流程，而不是某一个命令机械执行两次。

---

## 13. 自愈必须按故障域执行

不能因为“网络不通”就直接执行大范围恢复。

必须先判断故障属于哪里。

故障域至少包括：

- 节点
- 代理核心
- System Proxy
- TUN
- Route
- DNS
- NRPT
- Firewall
- 流量规则
- 本地物理网络
- 检测系统自身
- 未知故障

原则：

> **故障归到哪个域，就优先只修哪个域。**

目标：

> **使用最小动作恢复真实可用。**

---

## 14. 自愈失败后的错误系统

连续两轮自愈后仍然失败：

> **停止继续自动修复，并向用户明确报错。**

不能只提示：

```text
连接失败
```

错误必须说明：

1. 哪里失败；
2. 具体表现；
3. 已经执行了什么自愈；
4. 已经尝试几轮；
5. 最终是否恢复；
6. 当前网络受到什么影响。

例如：

```text
节点连接失败
当前节点：日本-01
故障位置：代理节点
原因：无法建立有效代理连接
自愈：已尝试 2 次，均未恢复
当前状态：该节点不可用
```

又例如：

```text
TUN 接管失败
当前节点：日本-01
故障位置：TUN
原因：Navo 虚拟网卡无法正常建立
自愈：已尝试 2 次，均未恢复
节点状态：节点本身可连接
当前状态：TUN 接管不可用
```

---

## 15. 错误等级

至少分为：

```text
正常
警告
错误
```

例如：

```text
节点可用
HTTPS 正常
出口正常
延迟 280 ms
```

这是：

> **质量警告**

而不是连接失败。

只有已经影响真实联网能力时，才进入错误和自愈。

Navo 不允许凭单一现象猜测故障来源。

无法可靠归因时，应明确显示：

> **原因未知**

---

## 16. 用户主动切换失败后的回退

当前 A 正常，用户主动切换 B。

如果：

1. B 验证失败；
2. B 第 1 次自愈失败；
3. B 第 2 次自愈仍失败；

则：

```text
明确报错 B 的失败原因
 ↓
自动恢复原节点 A
 ↓
重新验证 A
```

原则：

> **用户主动切换失败，不应把用户留在失败节点上。**

---

## 17. 当前活动节点自身故障

如果不是用户主动切换，而是当前正在使用的 A 自己发生故障：

```text
A 异常
 ↓
第 1 次自愈
 ↓
失败
 ↓
第 2 次自愈
 ↓
仍失败
 ↓
自动寻找同类型的其他可用节点
```

最高优先级：

> **优先保证用户重新获得可用代理网络。**

---

## 18. 机场与独立代理必须分通道

机场与独立代理属于两个不同的自动切换通道。

### 18.1 机场通道

机场节点故障后：

- 只在机场节点池寻找替代节点；
- 可以对用户保存的机场节点进行按需检测；
- 不可用 / Timeout 节点直接排除；
- 对剩余可用节点通过延迟、测速等质量指标排序；
- 优先尝试质量最好的节点；
- 最终仍以真实联网验证为成功标准。

### 18.2 独立代理通道

独立代理故障后：

- 只在独立代理池寻找替代线路；
- 不自动切换到机场。

### 18.3 禁止自动跨类型切换

```text
机场故障      ×→ 独立代理
独立代理故障  ×→ 机场
```

原则：

> **机场走机场，独立代理走独立代理。**

---

## 19. 节点质量检测

Navo 不需要长期、高频地对所有非活动节点持续测速。

### 19.1 正常状态

平时：

- 重点监测当前 Active Node；
- 其他节点保持静默；
- 不持续消耗大量网络与系统资源。

### 19.2 用户主动测速

用户进入节点列表并主动点击测速时：

```text
按需检测
 ↓
可用性
 ↓
延迟
 ↓
测速
 ↓
排序展示
```

### 19.3 故障自动切换

当前节点故障且自愈两次失败，需要寻找替代节点时：

```text
按需静默检测同通道候选节点
 ↓
剔除 Timeout / 不可用节点
 ↓
质量排序
 ↓
选择优先候选
 ↓
真实联网验证
 ↓
成功后切换
```

原则：

> **平时静默，按需检测。**

---

## 20. 当前总体架构关系

```text
用户
 │
 ▼
UI
 │
 ▼
连接协调器
 │
 ├───────────────┐
 ▼               ▼
节点域          接管域
 │               │
 ▼               ├─ System Proxy
Core 域          └─ TUN
 │                    │
 │                    ▼
 │                网络控制域
 │
 └───────────────┐
                 ▼
              实际代理链路
                 │
                 ▼
              真实联网验证
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
     成功                 失败
       │                   │
     COMMIT             自愈系统
                           │
                       最多两轮
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
                恢复               报错/回退/切换
```

观测系统独立存在：

```text
代理与网络观测域
│
├─ 所有代理状态
├─ 所有 TUN 状态
├─ 当前接管方式
├─ 当前节点
├─ 直连出口 IP
├─ 代理出口 IP
├─ 延迟
├─ 波动
├─ 丢包
├─ 上下行流量
└─ 当前真实可用性
```

原则：

> **观测可以看全局，控制只能控制 Navo 自己。**

## 21. 已确认的最高级架构原则

### 原则 01：全局可见，自身可控

Navo 可以观察所有代理相关状态，但只允许控制自身资源。

### 原则 02：唯一活动节点

任意时刻只有一个正式 Active Node。

### 原则 03：接管唯一

System Proxy 与 TUN 统一管理且互斥，任意时刻只能启用一种。

### 原则 04：策略通用

Global / Blacklist / Whitelist 与具体接管方式解耦。

### 原则 05：领域不越权

每个领域只操作自己的资源。

### 原则 06：跨域只有一个协调者

Connection Coordinator 负责跨领域执行顺序，各领域不能互相随意调度。

### 原则 07：观测并行，控制串行

任何网络状态修改必须通过统一事务串行执行。

### 原则 08：真实可用才算成功

Core 启动、配置成功、端口监听都不能单独代表代理成功。

### 原则 09：失败先自愈

真实验证失败后进入故障归因与自愈。

### 原则 10：最多两轮自愈

两轮仍失败立即停止继续自动修复。

### 原则 11：错误必须可归因

必须尽量告诉用户节点、Core、TUN、DNS、Route 等具体哪个域出了问题；无法确认时明确标记未知。

### 原则 12：主动切换失败要回退

A → B 失败时恢复 A。

### 原则 13：活动节点坏掉优先恢复可用

活动节点两轮自愈失败后，在同类型代理通道中寻找新的可用节点。

### 原则 14：机场与独立代理不串线

机场自动切换只走机场，独立代理自动切换只走独立代理。

### 原则 15：非活动节点平时静默

只有用户主动测速或故障切换需要候选节点时，才按需进行批量检测与排序。
